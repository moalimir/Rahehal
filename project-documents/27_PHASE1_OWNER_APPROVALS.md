# Phase-1 owner approval packet

This packet is the release gate for production infrastructure and managed identity. Engineering defaults are intentionally explicit, but **no row is approved merely because code or documentation exists**. The named human owner must record approver identity, date, scope, and any conditions in the table below before provider resources or production credentials are created. Local Linux containers, synthetic data, ephemeral databases, and standards-compatible development providers may be used to implement and test portable boundaries while these decisions remain pending; they confer no production approval and must not contain real identity evidence or confidential production data.

## Owner decision record (2026-08-27)

Approver: **project owner**, recorded through this delegated working session; the owner directed acceptance of the engineering defaults for these named decisions. No provider secrets, tokens, or private keys are recorded here.

- **Tenancy boundary (DEC-2026-011) — accepted.** The `organization` / `solver` / `platform` tenant model, one owning tenant per protected row, multi-tenant memberships, solver-company-as-`team`-workspace, and cross-tenant reach only through `access_grant` are the frozen semantics. This unblocks encoding tenant-kind and workspace-kind compatibility constraints in the first production migration (roadmap Phase A). Reversal requires a new migration and security review.
- **Applicant eligibility projection (DEC-2026-010) — accepted.** `allowedApplicantTypes` is authoritative and `ApplicantScope` is its derived coarse projection; the scope is never independently authored and never widens the detailed allow-set. This is the eligibility source of truth for challenge authoring, the API, and future persistence.
- **Residency — accepted as the pilot policy default,** condition: **a single named approved region with no data egress** is the binding rule; the concrete region/provider, subprocessors, backup/DR locations, and support-access terms bind only at provider selection, and **qualified legal/privacy confirmation remains required before any real confidential or identity data enters a hosted environment** (roadmap Phase C hardening / Phase E pilot). Local synthetic-data engineering proceeds now.
- **Classification — accepted as the pilot policy default.** The four tiers and their default mapping (public projections `public`, operational metadata `internal`, proposals/brief internals `confidential`, identity/contract/payment evidence `highly_sensitive`; downgrade requires ops approval + reason) are the working contract for schema, access, files, and any future AI egress. Same condition: qualified legal/privacy confirmation of the tier matrix, retention, and key-ownership before real data.
- **Identity, secrets, storage, and hosting providers — deliberately deferred by the owner.** No provider is selected yet. Engineering builds a provider-neutral OIDC integration (authorization code + PKCE, issuer/audience validation, revocation) against a **local test IdP** per roadmap Phase A (simple login), with MFA/rotation/KYB deferred to Phase C, and provider-neutral storage/secrets/IaC contracts, until the owner selects providers from measured requirements. Production credentials and external environments are not provisioned until then.

The two `pilot default` rows are engineering-direction acceptances by the accountable owner; they set the plan of record and unblock local implementation. They do **not** substitute for the qualified legal/privacy review named in their owner column, which is a Phase-6 gate before an external pilot.

## Provider inputs required before external environments or production identity

Local engineering may define provider-neutral ports, validation, migrations, and integration tests. It must not guess these deployment values or provision external preview/staging/production resources without them:

1. Cloud/hosting provider and exact region for dev, test, preview, staging and production.
2. IaC tool/provider account structure, state backend and production break-glass owner.
3. Secret manager/KMS, key-residency boundary and credential-rotation owner.
4. Managed OIDC provider, issuer URL/tenant, approved redirect domains, client-registration model and MFA policy.
5. Environment domains, DNS owner, artifact/container registry and deployment approval path.
6. Approved data subprocessors, log/backup retention, RTO/RPO, and whether preview may use synthetic data only (recommended: yes).

## Approval rule

An approval changes a row to `accepted`, records the human approver and ISO date, and links the supporting legal/security/provider evidence. A chat instruction to “use the defaults” is sufficient only when the sender is the named accountable owner and explicitly identifies the decisions being accepted. Provider secrets, tokens and private keys never belong in this document or the repository.
